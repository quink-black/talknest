# CLI 客户端 AEC 实测

2026-09-13，x86 台式机（Ubuntu，PipeWire 1.0.5，PortAudio V19.6），分支
`cli-client`。结论先行：**DTLN-AEC 实现经合成回环验证正确（29~41 dB）；
蓝牙 HFP 链路因时延抖动无法做参考对齐型 AEC，该设备类用半双工**。

## 设备

| 设备 | 接口 | 麦克风 | 扬声器 |
|---|---|---|---|
| Jabra EVOLVE 20 | USB | 有（实测采集正常，硬件自带 UC 级 DSP） | 耳机 |
| 蓝牙音箱 51:60:06:A2:EA:2C | HFP (mSBC, 16 kHz) | 有 | 外放（高回声） |

## 合成回环：验证模型链路

远端取真实回复音频，回声 = 延迟衰减副本（-12 dB）+ 微小噪声，
`dtln_aec_128`，XNNPACK CPU：

| 真实回声时延 | 最优补偿 | ERLE |
|---|---|---|
| 10 ms | 0 ms | 29.3 dB |
| 50 ms | 25~28 ms | 38~39 dB |
| 80 ms | 50~60 ms | 41.0 dB |

规律：最优补偿 ≈ 真实时延 − 25~30 ms，即模型有自己的时延容忍带
（残余失配 10~50 ms 有效），补偿值必须扫描不能拍脑袋。处理速度
RTF 0.030（5.84 s 音频 0.177 s，33 倍实时）。

## 蓝牙真实回环：参考对齐失败

`--aec-bench` 以互相关时延为中心扫描 0~780 ms，ERLE 全程平坦
（13.0 dB @ 0 ms 缓降至 7.6 dB），**无对齐峰**。分段互相关诊断
（每段 ~1.3 s）：

| 段 | 相干系数 | 峰位 |
|---|---|---|
| 2 | 0.047 | 172 ms |
| 3 | 0.109 | 227 ms |
| 4 | 0.036 | 1090 ms |
| 5 | 0.044 | 985 ms |

相干系数 0.01~0.11、峰位秒级漂移：HFP 的缓冲时延抖动把回声路径抹散，
固定对齐的参考型 AEC（无论 DTLN 还是 WebRTC）在此类链路上原理性失效。
这正是设计文档预判的"时钟漂移会显著削弱 AEC"，实测比预判更严重。

## 全链路声学闭环（蓝牙外放 → 蓝牙麦克风采回）

TTS 合成"兔子用英文怎么说？"从蓝牙音箱外放、蓝牙麦克风拾取：

- **全双工（dtln）**：第一轮正常，但回复的"跟我读一遍"被拾回并触发
  服务端 barge-in 误判，随后连环幽灵轮次（回声被转写成"读一遍。"
  "去弹钢琴。"）。符合"回声无法对齐就一定误触发"的推演。
- **半双工（none）**：一轮干净完成，转写正确、回复完整、`listening`
  恢复、无幽灵轮次。回声环境下此模式的正确性得到真机验证。

一个待观察项：全双工那次转写成了"裤子"（半双工为"兔子"）——DTLN 在
低回声场景下的处理可能轻微影响 ASR，样本太少不下结论。

## 结论

1. 设备有硬件 AEC（Jabra 类 UC 设备）或干净拾音时：`--aec dtln` 做残余
   清理，真机 ERLE ~10~13 dB（硬件已消掉大半，剩余本就有限）。
2. 蓝牙音箱类高回声设备：用 `--aec none`（半双工）+ 回车打断，这是
   实测唯一干净的模式。服务端 `barge_in_*` 调参是辅助手段，不是出路。
3. 软件对齐型 AEC 的适用边界被实测画出来了：稳定时钟的同源设备。
   蓝牙免提不在其列。
