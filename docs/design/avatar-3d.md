# 4 视图 → 3D 形象：技术方案

前提素材：`whale.webp` 四视图设定图（正/背/左/右，正交视图，已能从正面
干净抠图）。目标：网页上的形象有 3D 感。

## 方案对比

### A. 精灵图旋转（伪 3D / 2.5D billboard）

把四个视图都抠成透明 PNG/webp，浏览器里维护一个虚拟朝向角 yaw，按
yaw 选帧显示，帧间用淡入淡出 + 水平压缩（scaleX）做过渡，就像展品在
转台上转。yaw 可以缓慢自动摆动，也可以跟随鼠标。

- 4 视图利用率：全部用上（0°/90°/180°/270°）。
- 工作量：小。抠图脚本参数化跑 4 次 + 前端 ~100 行（角度状态机 +
  帧切换 + 过渡），零依赖，和现有 no-build 风格一致。
- 效果：只有 4 个角度，转动是"跳帧+过渡"，不是真连续旋转；但配上
  现有的呼吸/说话弹跳，观感和"3D 小手办"接近。
- 风险：低。背面视图的"脑后"是纯背面，对话时转过去太久不合适，
  所以自动摆动范围要限在 ±60° 以内（正/左/右三帧为主，背面只做
  彩蛋式短暂展示，或干脆不进自动循环）。

### B. Live2D

把正面图拆成图层（头发前/后、脸、眼、嘴、身体各部件），在 Live2D
Cubism Editor 里建模绑骨，网页用官方 Cubism Web SDK 播放。这是二次元
形象"活起来"的工业标准：头部跟随、呼吸、物理摆动都能有。

- 4 视图利用率：只用正面（侧/背面当拆分参考）。
- 工作量：大。拆图补画 + 编辑器绑定是以"天"计的美术工作；SDK 是
  专有软件，引入要看 Live2D 发布许可（小项目有免费档，但有条件）。
- 效果：四个方案里"生动"的上限最高，但它是 2D 形变，不是 3D。
- 风险：工作量和许可。

### C. image-to-3D 生成真 3D 模型 + Three.js

本机 12G GPU 可以跑开源 image-to-3D（TRELLIS、TripoSR 这类），喂正面
视图（侧/背面可作补充条件）生成带贴图的 GLB，前端用 `<model-viewer>`
或 Three.js 展示，鼠标拖动旋转。

- 4 视图利用率：正面为主，其余作条件（这些模型主要吃单图）。
- 工作量：中到大，且质量不确定——二次元脸在这类模型上翻车率高
  （五官糊、比例崩），需要反复试。
- 真正的硬伤是**动画**：生成的模型没有骨骼。要动就得进 Blender 绑骨
  或用 Mixamo 自动绑定（Q 版二头身比例 Mixamo 识别很差）。不绑骨就
  只能整体旋转，跟方案 A 比只多了"任意角度"，却付出了 WebGL +
  Three.js（约 600KB 依赖）+ 质量风险 + 美术返工。
- 风险：高投入、质量不可控、动画链路长。

### D. NeRF / 3DGS 重建

4 张正交视图对 NeRF/3DGS 来说少了两个数量级（需要几十张环绕拍摄）。
不可行，列出来只为排除。

## 结论：已实现 A

2026-09-19 按方案 A 落地：四帧（正/左/背/右，右视图镜像出反方向）
底部对齐叠放，yaw 缓动选帧；空闲 ±70° 游走、鼠标跟随 ±25°、说话时
面向正前、空闲几十秒随机转一整圈。呼吸/说话弹跳/思考倾斜原样保留。

## 建议（当时）

**先 A，不够再 B，C 只做一次性实验。**

A 是唯一"把 4 视图直接用满"的方案，成本是一下午，且随时可以撤。
如果 A 的跳帧感不能接受，说明要的是"生动"而不是"3D"——那是 B 的
领域。C 值得用本机 GPU 试一次看生成质量（不行就放弃），但即便模型
不错，动画仍然是绕不过去的美术工作。

## 方案 A 的具体设计（已实现）

1. 抠图：`scripts/extract_avatar_views.py <sheet> web/`。四个角色在
   设定图上是互不连通的连通域，按各自边界裁（尾巴会越出所在列，不能
   按 300px 列宽硬切——正面那张原来的尾巴尖就是这么被切掉的）。
   脚底靠 CSS bottom 对齐，不需要逐张调基线。
2. 前端：把现在的 `<img id="avChar">` 换成一个容器，里面 4 张 img
   叠放，按 yaw 选一张 opacity=1，相邻一张低透明度做过渡；yaw 用
   rAF 缓动追踪目标角度。状态动画（呼吸、说话弹跳、思考倾斜）原样
   保留，作用在容器上。
3. 交互：空闲时 yaw 在 -60°..+60° 间缓慢游走；鼠标在页面上移动时
   轻微跟随（±30°）；说话时可以面向正前。
4. 不碰协议、不碰服务端。
